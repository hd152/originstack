# Native (Rust) kernels: per-kernel history and measurements

> Moved verbatim from CLAUDE.md on 2026-10-07 to keep that file small. This is history and measurement narrative, not current instructions; where it disagrees with the code or CLAUDE.md, the code wins. Since this was written the 2026-10 cleanup removed, among others: Python `drizzle_combine`/`_lanczos_resample_frame`, `registration.compute_patch_quality_map`/`patch_scores_to_map`/`apply_shift`, `denoising.reduce_stars`, `debayer.remove_hot_pixels_rgb`, `color_calibrate.synthetic_channel_flux`, `banding.banding_strength`, `sky_model.remove_physical_sky`/`moon_illuminated_fraction`, `ui_events.restretch`/`preview_jpeg` and the retained float16 preview source, `PreviewCanvas.replace_pixels`, `io_*.is_*_file`, `frame_store` `release()`, `tools/benchmark.py`, `tools/reprocess_bg.py`; Rust `online_sigma_clip_combine`, `white_balance_apply_inplace`, the old `patch_weighted_sigma_combine` (only `_fast` remains), f64 `proper_coadd_accum`, the `ORIGINSTACK_LANCZOS_EXACT` switch; `row_parallel`/`row_parallel_pair` merged; transient triage (tract) is behind the off-by-default Cargo feature `triage`.

### Native (Rust) acceleration
[ext/astro_native/](ext/astro_native/) is a PyO3/maturin crate of hot-path kernels, all with a numpy fallback. Coverage:
- **transient triage inference** (`ext/astro_native/src/lib.rs` `mod transient_triage`, `src/transient_triage.py::score_candidates`, `--transient-triage`): the crate's one ONNX kernel, on the pure-Rust **`tract`** runtime (~120 transitive crates; it lengthens the crate's first build noticeably) -- no percentile stretch, no resize (candidate stamps arrive already extracted at a fixed size and per-channel sigma-normalized in Python), no multi-head metadata decode, just a batched tract forward pass over `(N, 3, size, size)` returning one sigmoid probability per candidate in a single call rather than one call per candidate. The forward pass runs under `py.detach` and `std::panic::catch_unwind`: `tract` parses an external `.onnx` and a malformed one can *panic* inside the parser (a `pyo3_runtime.PanicException`, a `BaseException` that slips past callers' `except Exception`), so it is converted to a plain `RuntimeError`; `panic = "unwind"` (not `"abort"`) in the release profile is what lets that unwind happen. Sessions are cached per `(model_path, size)`. **Deliberately has no numpy/onnxruntime fallback yet** -- unlike every other native kernel in this file, a source checkout without `astro_native` built simply cannot use `--transient-triage` (self-disables with a warning) until one is added.
- **Stacking combines** (`src/stacking.py`): `sigma_clip_combine` (~37×), `esd_combine` (~24×), `percentile_clip_combine` (~13×), `median_combine` (~6×). ESD's Student-t critical-value table is precomputed in Python (`_esd_lambda_table`) and passed to Rust — exact parity, no stats crate. Native path is taken when a rejection mask is not requested and the input is a C-contiguous float32 `(N,H,W,C)` array; the aligned stack memmap qualifies, so Rust views it zero-copy and the streaming memmap model is preserved. (`trimmed_mean_combine` was removed 2026-08 — Python and Rust — once recognized as functionally identical to `percentile_clip_combine` at matching params, just parameterized by trim-fraction instead of percentile bounds.)
- **Linear Fit Clipping** (`src/stacking.py` `linear_fit_clip_combine`, `--stack-method linear_fit`): PixInsight's algorithm — sorts each pixel's per-frame stack ascending (order statistics), fits a line to value-vs-rank by least squares, rejects samples whose residual from that fit exceeds `sigma_low`/`sigma_high` times the residual scale, refits on survivors, iterates. More robust to non-Gaussian tails than sigma-clip's mean/std test since it doesn't assume the per-pixel distribution across frames is Gaussian, just that it's locally near-linear in sorted order. No independent open-source reference implementation exists to bit-validate against (unlike Malvar/Menon2007) since PixInsight is closed-source — validated instead via a numpy mirror (`_linear_fit_clip_tile`) checked for native/numpy parity plus a synthetic-outlier-injection test (`tests/test_native.py`) confirming a single wild sample per pixel doesn't survive into the combined result.
- **Inverse-variance-weighted combine** (`src/stacking.py` `ivw_combine`, `--stack-method ivw`): the Gauss-Markov-optimal linear combiner — weights each frame by `1/noise²` using that frame's own measured Phase 1 background sigma (a real statistical optimum under a per-frame-homoscedastic noise model, unlike `--weight-noise`'s ad-hoc multiplicative heuristic). Optionally adds a per-pixel Poisson shot-noise term (`--config ivw_gain`, electrons/ADU) so brighter regions are correctly down-weighted relative to sky background in noisier frames — this is why it still routes through the native kernel's per-pixel loop rather than a single static-weight numpy broadcast, even though the no-gain case has no iteration or sorting at all. Does not reject outliers (cosmic rays/trails get a small nonzero weight, not zero) — meant to complement this pipeline's existing per-frame pre-filters (`--cosmic-ray-rejection`, `--trail-reject`), not replace them.
- **Drizzle resample** (`src/stacking.py`): both drizzle paths route through `warp_affine_lanczos3` (~26×, all channels in one pass; true Lanczos-3 vs the scipy order-5 quintic approximation it replaced). The kernel's separable fast path covers any diagonal matrix — drizzle's no-rotation `diag(1/scale)`+offset mapping as well as pure translations. `--drizzle-pixfrac < 1.0` (tent-kernel footprint shrink, defined in input-pixel space so it stays correct under rotation) is applied as a per-frame numpy weight after the Rust warp, not inside the kernel itself.
- **Fused patch-weighted combine** (`src/stacking.py` `run_stacking_phase`): `patch_weighted_sigma_combine` (~100×) — the consensus/patch-weighted path did two numpy passes (sigma-clip `return_mask=True` + `patch_weighted_mean_combine`); the Rust kernel fuses sigma-clip rejection + quality weighting in one pass with no `(N,H,W,C)` mask array. Used for the sigma_clip/winsorized patch methods.
- **Online (streaming) sigma-clip** (`src/stacking.py`, used by `--stream`/`src/stream_stack.py`): `online_sigma_clip_seed_burnin` seeds a running Welford `(mean, m2, n_acc)` state from a small MAD-rejected burn-in window, and `online_sigma_clip_fold_frame` folds one further frame in at a time — the per-frame step of a true frame-at-a-time streaming combine, as an alternative to materializing the whole `(N,H,W,C)` aligned stack `sigma_clip_combine` needs. `online_sigma_clip_fold_frame` updates its `(mean, m2, n_acc)` state arrays **in place** (the one exception to this file's alloc-and-return convention) — reallocating and copying three full-resolution float64 arrays on every accepted frame was real allocator churn at full sensor resolution. `online_sigma_clip_combine` (whole-array, benchmark-only) is also available for throughput comparison against the batch kernels.
- **Per-frame warp** (`src/registration.py` `apply_transform`): `warp_affine_lanczos3`, a 2D Lanczos-3 affine/shift resample (~5×). CPU path only (GPU unchanged). This is a quality-validated change, not numeric parity: FWHM and flux match scipy order-3, and the mild Lanczos ringing is incoherent across dithered frames (averages to zero in the stack).
- **Anisotropic diffusion** (`src/denoising.py` `anisotropic_diffusion`): native Jacobi iteration with periodic boundary (~37×), exact parity.
- **DBE surface fit + patch sampler** (`src/background.py`): `dbe_fit_surface`, Gaussian-weighted local-linear regression with Tukey-biweight IRLS (~2.4× over the scipy RBF it replaced), and `dbe_sample_patches`, the per-patch rejection cascade (~31×). Not just a speedup — the RBF (thin-plate spline + hard outlier-rejection loop) was unbounded and could extrapolate wildly into rejected-sample gaps near bright stars; the local fit is bounded near the sample values by construction. Numpy mirror in `_dbe_fit_surface_numpy`, parity-tested. **`patch_entropy_batch`**: `dbe_sample_patches`'s own docstring calls the entropy filter "cheap, operates on the small per-patch result" -- true per-call, but under `--auto` (`entropy_bg=True` for most target types) it runs on every DBE pass regardless of session size, and profiling a real run found `_filter_sampled_patches`'s Python loop over up to `Config.DBE_MAX_SAMPLES` (4000) candidate patches, each calling `np.histogram`, costing 4.2s on its own. Fused into one rayon-parallel native pass. Not bit-exact -- numpy's histogram fast path has a floating-point edge-correction pass (compares each value against the actual `linspace` bin edges and nudges the index where rounding put it a bin off) this doesn't replicate, so entropy values agree to ~3e-4 absolute on a real-shaped case, not bit-for-bit; immaterial for what this feeds (a median+MAD outlier threshold over thousands of patches). Cut a real profiled run's Post-process time by ~2.6s. **`_fit_background_surface`'s coarse-grid upsample is bilinear (`order=1`), not cubic (`order=3`)**: the very next line blurs the surface again (`sigma=patch_size*0.5`, typically >=32px), same "nothing left for cubic's curvature term to recover" reasoning as `gaussian_filter_ds`'s own upsample -- validated directly (not assumed) against real `_dbe_regression_coarse_grid` output, post-blur mean diff <0.1, max <1.0 (`tests/test_dbe_gradient.py::test_fit_background_surface_bilinear_upsample_matches_cubic`). `wavelet_background_extraction`'s sibling `zoom(order=3)` call (no follow-up blur there) was deliberately left alone -- it has no real quality test (only a mocked one in `test_sky_model.py`) and a synthetic check was inconclusive, so there wasn't enough evidence to change it with confidence.
- **Cosmic-ray rejection** (`src/stacking.py` `lacosmic_reject`): `lacosmic_reject_native`, L.A.Cosmic-style Laplacian spike detection + 5×5 median replacement, f32 internally (~2×+ vs numpy; the memory-traffic halving matters more than raw compute under 16-way ProcessPool contention).
- **Median filter** (`median_filter_native`): windowed median (reflect boundary) used by lacosmic and the hot-pixel detectors. Interior fast path with contiguous reads; 3×3 uses Paeth's 19-op branchless median network (~13×), 5×5 quickselect (~1.6×).
- **Malvar-He-Cutler debayer** (`src/debayer.py` `debayer_malvar`, `--debayer-method malvar`, the default until 2026-10 -- now `rcd`): the true published algorithm (Malvar, He & Cutler 2004), not an approximation — sparse per-pixel tap gather (each output pixel needs at most 2 of the 4 kernels; its own channel is the raw sample) rather than 4 whole-image convolutions, with an interior fast path (no per-tap boundary-index modulo) for all but a 2px border (~2×). Replaces the old cv2 `COLOR_BAYER_*_EA` path, which required requantizing to uint16 first (real precision loss) and only worked when cv2 was installed; this runs on the native float32 data with no dependency. Numpy mirror (`_debayer_malvar_numpy`) validated bit-exact against the `colour-demosaicing` package's reference Malvar2004 implementation across all 4 Bayer patterns (validation-only dependency, not required at runtime — see `tests/test_debayer_malvar.py`).
- **Menon (2007) DDFAPD debayer** (`src/debayer.py` `debayer_menon2007`, `--debayer-method menon2007`): staged full-array passes (green directional interpolation, gradient-diffused direction decision, R/B fill, refining pass), each parallelised across rows — not fusible into one per-pixel gather like Malvar above, since the direction decision at each pixel depends on a 5x5-diffused gradient of a shifted colour-difference signal computed over the whole frame first. One gotcha worth flagging for future kernel ports: the 5x5 gradient-diffusion kernel is not 180°-symmetric, and `scipy.ndimage.convolve` flips the kernel (true convolution, not correlation) — the first native version's sparse tap table was built as a direct correlation gather and silently produced wrong results (55% of pixels off, caught by the native/numpy parity test) until every tap's `(dy, dx)` was negated to compensate. Every other kernel in this file's tap tables happens to be symmetric, so this asymmetry (and the convolve-vs-correlate distinction) hadn't come up before. Numpy mirror (`_debayer_menon2007_numpy`) validated bit-exact against `colour-demosaicing`'s reference Menon2007 implementation across all 4 Bayer patterns and both `refining_step` settings (`tests/test_debayer_menon2007.py`). Not the default — see "Debayering options" below for why.
- **Bilateral filter** (`src/denoising.py` `bilateral_denoise`, `--denoiser bilateral`): joint (colour-space) bilateral filter — per-pixel Gaussian-weighted average over a `2*radius+1` window, weight = spatial Gaussian x colour-similarity Gaussian, colour distance computed jointly across all 3 channels (matches cv2.bilateralFilter's multi-channel behaviour, avoids colour fringing at edges independent per-channel weighting would cause). Replaces cv2.bilateralFilter, the last cv2-only feature with no fallback — this codebase has no cv2 dependency left at all. Numpy fallback (`_bilateral_filter_numpy`) validated bit-exact against the native kernel (same boundary convention: numpy's `np.pad(mode='reflect')`, despite the name, is a non-edge-duplicating reflection — the same convention scipy calls `'mirror'`, which is what the Rust kernel's `mirror_idx` implements).
- **2D wavelet transform** (`src/wavelet.py` `dwt2_native`/`idwt2_native`, used by `--denoise` wavelet denoising and `compute_multiscale_entropy`): direct closed-form tap-sum port of `_dwt_1d`/`_idwt_1d`'s pad-then-`np.apply_along_axis`-then-`np.convolve` (which loops in pure Python over every row/column of every level — this runs on every default stack, unlike the other kernels below which are opt-in). Kept in **f64 throughout**, unlike every other kernel in this file: multi-level `wavedec2`/`waverec2` chains several of these calls per plane, and rounding to f32 at each level's Python/Rust boundary compounds across levels — this is the one kernel where that would have broken the existing bit-exact-vs-pywt parity tests (`tests/test_wavelet.py`), caught immediately on first build (20% of pixels off by up to 1.5e-4, an f32-rounding-scale error, not a logic bug) and fixed by switching the coefficient arrays to f64.
- **Blind (unknown-rotation) rigid star-pattern match** (`src/blind_match.py` `match_rigid_unknown_rotation`, used by `--merge`'s cross-night registration and the in-session fallback when near-zero-rotation RANSAC fails): the hypothesis-scoring loop (up to `_MAX_HYPOTHESES`=20000 distance-matched pair-of-pairs, each requiring a nearest-neighbour consensus count) ported as a brute-force O(n·m) nearest-neighbour search — n/m are capped small (`max_stars`, default 40) by the caller, so what this actually removes is the per-hypothesis Python-loop + scipy `cKDTree.query` call overhead, not the underlying query cost, which is trivial at this scale either way. The final all-inliers Umeyama refit stays in Python (`src/affine_fit.py::_umeyama_2d`), called once per match, not per-hypothesis. Numpy mirror (`_match_hypotheses_numpy`) parity-tested against the native kernel on synthetic rotated star fields (`tests/test_native.py`).
- **Bayer hot-pixel fix, sigma-clipped median, and sparse hot-pixel replacement** (`src/debayer.py`, all three on the default Phase 1 hot path, found via profiling a real session): `_fix_hot_bayer` (`mode='bayer'`) was calling `scipy.ndimage.median_filter` directly on each 2x2 Bayer sub-channel instead of the already-existing native `median_filter_native` dispatcher (`_median_filter3`) — because those sub-channels are non-contiguous strided views (`result[dy::2, dx::2]`) and the dispatcher's fast-path guard requires C-contiguous input. Fixed by routing through a contiguous copy first (`np.ascontiguousarray(sub)`) — no new Rust kernel needed, just a dispatch fix; ~7.5x faster on its own (242ms → 32ms on a 1936x1096 frame, measured in-process with warm-up to avoid cold-start noise). `sigma_clipped_median_native` ports `_sigma_clipped_median` (iterative sigma-clip + median, quickselect-based like `median_inplace` but f64 throughout since it returns a single scalar with no coefficient-chaining concern) — shared by `green_equalize` (G1/G2 balance) and `_equalize_bayer_grid` (per-Bayer-position sky level), both calling it several times per frame on quarter-resolution strided views. `hot_pixel_box_replace_native` replaces `_fix_hot_rgb_impl`/`_fix_hot_mono_impl`'s `scipy.ndimage.uniform_filter(ch, size=3)` replacement step, which computed the box mean over the *entire* channel just to keep a handful of masked (hot) positions — the native kernel computes the 3x3 box mean only at flagged positions, a sparse win on top of the native-vs-scipy win. Together these cut a real sequential (single-threaded) profile of Phase 1 from 173.5s to 93.3s on a 214-frame session (`_fix_hot_bayer` 52.0s→6.7s, `_fix_hot_rgb_impl` 33.6s→13.8s, `_sigma_clipped_median`/`_equalize_bayer_grid` region 31s→16.4s) — the wall-clock improvement under full parallelism is smaller (Quality+Load is already ~4x parallelized across cores, and these three functions are only part of its total cost), but the underlying per-frame work is genuinely ~46% cheaper.
- **Gram-matrix thin-SVD trick** (`src/robust_pca.py` `_thin_svd_wide`, used by `--master-method robust_pca`'s IALM solver): `gram_matrix_wide` (`D @ D.T` for a wide `(N, P)` matrix, rayon-parallel over the `N*(N+1)/2` upper-triangle pairs, mirrored to the lower triangle) and `small_times_wide` (`small @ data` for a small `(N,N)` left operand and wide `(N,P)` right operand, rayon-parallel over output rows, axpy-style accumulation to keep each inner loop reading a data row sequentially rather than striding by P) — together the two GEMMs of eigendecomposing the small `N x N` Gram matrix instead of calling `np.linalg.svd` directly on the full wide matrix. Measured on the realistic robust-PCA shape (N=20, P=18M): direct `np.linalg.svd` 37.8s, the Gram trick in plain numpy 15.7s (~2.4x — numpy's own SVD isn't specialized for this shape), with these native kernels 7.9s (~4.8x on top of the algorithmic win, ~9x combined) — numpy's own `@` got zero benefit from this machine's cores at this shape (8.1s default-threaded vs 8.9s forced single-threaded), which is the headroom the native kernels close. Numpy mirror is `_thin_svd_wide`'s own fallback path (same function, not a separate mirror), so no separate parity test file — `tests/test_robust_pca.py` validates the whole decomposition end-to-end instead.
- **IALM per-iteration fusion** (`src/robust_pca.py` `robust_pca_pre_svd_input` + `robust_pca_iterate`, used by `robust_pca_decompose`): profiling a real `--flat-from-lights` run (auto-triggered by `--auto` when no flat frames exist, N=10 sampled lights, P=6.25M mono pixels) found `robust_pca_decompose` spending 100s of a 126s total in plain-numpy elementwise arithmetic around the SVD (`D - S + Y/mu`, the S soft-threshold, `D - L - S`, `Y += mu*residual`, the residual norm) — roughly a dozen full-`(N,P)`-array passes/iteration, each its own temporary, not counted in `_thin_svd_wide`'s own (already-native) time at all. `robust_pca_pre_svd_input` fuses the first into one native pass; `robust_pca_iterate` fuses the rest into one native pass, writing `S`/`Y` in place (allocated once outside the loop, not re-allocated every iteration) and returning the residual's Frobenius norm directly. Per-element arithmetic (including matching `np.sign`'s 0-at-exactly-0 semantics, not `f64::signum`'s +-1) is bit-identical to the numpy reference; the norm is a parallel-chunk reduction, so only close to numpy's sequential sum (immaterial — it's just a convergence-tolerance check). Cut this same real case from 126.9s to 62.5s (~2x). Profiling *that* found the next bottleneck was no longer numpy at all: the L-update's `(U * sigma_shrunk) @ Vt` reconstruction — the exact same small-`(N,N)`-times-wide-`(N,P)` shape `_thin_svd_wide`'s own Gram-trick GEMM is — was calling plain `np.matmul`, and this machine's numpy has no optimized BLAS (`numpy.show_config()` reports `blas: name: auto`; measured ~1.4 GFLOPS, reference-BLAS speed), so that one line was 32.9s of the post-fusion 62.5s on its own. Routing it through the already-existing `small_times_wide` native kernel instead cut the real case to 45.4s (~2.8x combined vs. the 126.9s baseline; full pipeline wall-clock on the same session 3m7.8s -> 1m46.0s). Numpy fallback is the original expressions (`np.sign`/`np.maximum`/`np.matmul`), unchanged and still exercised by `_HAS_NATIVE` toggled off in tests. End-to-end native-vs-numpy-fallback parity (not just the individual kernels) in `tests/test_native.py`.
- **Gaussian blur** (`gaussian_filter_native`, `src/background.py`'s `_gaussian_blur` wrapper + `gaussian_filter_ds`): `correlate1d` (the C function `scipy.ndimage.gaussian_filter1d` calls per axis) was the single largest self-time item in every full-pipeline profile taken this session -- ~30 call sites project-wide (DBE, chroma denoising, local contrast, structure-tensor coherence, edge-band correction, registration, star masking, and more). From-scratch separable reimplementation (two rayon-parallel correlate1d-style passes, row-wise then column-wise) of scipy's default `mode='reflect'` behaviour: same kernel formula (`radius = floor(truncate*sigma + 0.5)`, normalised Gaussian PDF samples, order-0), same edge-duplicating boundary (`reflect_idx`, shared with the hot-pixel kernels). Not a port -- parity is numerical, verified to double-precision rounding (rtol/atol 1e-9) across sigma 0.8-96 and two shapes, not bit-exact, since the two implementations sum in a different order. ~4x faster at small sigma (0.8-5), ~1.3-1.5x at the large sigmas `gaussian_filter_ds`'s downsampled branch uses (24-96) -- larger sigma means a wider kernel radius, so the per-tap loop cost grows and narrows the win. `_gaussian_blur` (2-D float only, transparent scipy fallback otherwise) preserves the caller's dtype (a first version silently upcast float32 to float64 -- the native kernel is always float64 internally like every other kernel in this file, and the wrapper wasn't casting the result back down; caught by a dtype-parity test before it could double the memory footprint of every float32 caller). Wired into every direct `gaussian_filter` call site project-wide that uses a plain scalar sigma on a 2-D array (`background.py`, `denoising.py`, `cli.py`'s master smoothing, `exposure_fusion.py`, `merge.py`, `moving_objects.py`, `noise_validation.py`, `postprocess.py`, `quality.py`, `registration.py`, `star_removal.py`, `trail_reject.py`). **`gaussian_blur_spatial`** (`src/background.py`) extends coverage to this codebase's `sigma=(s, s, 0)` call sites -- blur each channel of an `(H, W, C)` array independently (never across channels) by looping `_gaussian_blur` per channel, same per-channel-native-call pattern as `postprocess.py`'s `_median_filter_per_channel`. Wired into `denoising.py::reduce_stars` (the default Phase 4 star-reduction step, `--no-star-reduce` to disable) and `exposure_fusion.py`'s Laplacian-pyramid up/downsample (`--hdr-blend-mode fusion`). Measured ~2.8x at a real full-res `(2033,3041,3)` shape, sigma=1.5 (495.6ms -> 177.7ms) -- lower than the 2-D kernel's own ~4x at that sigma since each channel still pays native-call overhead separately, not fused into one 3-D pass.
- **PSF-matched drizzle kernel + IBP super-resolution** (`src/stacking.py`, `--drizzle-kernel psf` and `--super-res-iters`): `warp_affine_kernel_table` is `warp_affine_lanczos3`'s sibling for an arbitrary (non-separable) precomputed tap-weight table instead of the fixed Lanczos-3 formula — lets drizzle resample with the session's own estimated PSF (`build_drizzle_psf_table`, a Wiener-regularized inverse filter of the PSF, not the raw PSF shape — using the raw shape measurably broadens stars, convolving an already-blurred profile with itself again) as a matched filter. No fast-path branch like Lanczos-3's separable case: a general Moffat/Gaussian PSF isn't X/Y-separable, so every output pixel gathers the full `(2*halo+1)^2` neighbourhood; numpy mirror is `_warp_affine_kernel_table_numpy`. `iterative_back_projection` (Irani & Peleg 1991, `--super-res-iters`) refines a drizzle output afterward in pure Python/numpy (no native kernel — the per-frame forward-simulate/back-project loop is FFT- and `affine_transform`-bound, not a hot inner-loop shape this file's kernels target): forward-simulates what each original frame should look like given the current estimate (inverse-warp + PSF blur via `scipy.signal.fftconvolve`), compares to what was actually observed, and back-projects the residual correction, reusing `_drizzle_matrix` (shared with the main drizzle resample loop) for the exact same per-frame affine mapping so the forward-simulate step is a literal inverse of the resample that built the initial estimate. Not compatible with `--elastic-registration` yet (IBP's forward model doesn't account for the local displacement field).

- **Continuum-subtraction moments** (`src/channel_combine.py` `continuum_scale_moments`, used by `optimal_continuum_scale`, `--continuum`): the naive approach re-scans the full masked pixel array once per swept scale to compute `scipy.stats.skew` directly — this instead exploits that the subtraction residual `narrowband - s*continuum` is *linear* in `s`, so its skewness at any scale is a closed-form polynomial of 7 scalar central moments computed once, an algorithmic win independent of native vs. numpy (verified exact to float64 precision against `scipy.stats.skew` at several scales before replacing the per-scale loop). The native kernel is the constant-factor win on top of that: two passes (mean, then central moments, deliberately mirroring the numpy fallback's own two-step logic rather than a single-pass raw-moment shift-formula that would need separate algebra to get right) fusing what numpy computes as ~7 separate full-array elementwise-power passes (`ap*bp`, `ap*ap*bp`, ...) into one pass per stage. Not rayon-parallelised — called once per `optimal_continuum_scale` call, not once per swept scale, so there's no outer loop multiplying its cost the way this file's per-frame kernels have.

- **IVW uncertainty map** (`src/stacking.py` `ivw_combine(..., return_sigma=True)`, `--uncertainty-map`): `ivw_combine_with_sigma` is a sibling of the plain `ivw_combine` kernel that also emits the per-pixel-per-channel summed inverse-variance weight (the combiner's own variance is exactly `1/wsum`), via a new `row_parallel_pair` driver (`row_parallel`'s gather-transpose pattern, generalised to a `work` closure that produces two per-pixel outputs instead of one). Kept as a separate function/driver rather than changing `ivw_combine`'s own signature, so that already-shipped, tested kernel's call sites stay untouched by what's an opt-in diagnostic path; duplicates `ivw_combine`'s per-pixel weighting loop rather than sharing it, accepted for the same reason.
- **Moffat wing fit** (`src/star_repair.py` `_fit_moffat_wing`, `--repair-stars`): scipy's bounded `curve_fit` calls back into a Python Moffat model every trust-region iteration — with up to 800 saturated stars x 3 channels per repair run, that per-call Python-callback overhead dominates, not the fit's own arithmetic (each wing is only tens-to-low-hundreds of pixels). `fit_moffat_native` is a from-scratch bounded Levenberg-Marquardt with the Moffat model and its analytic Jacobian both inlined in Rust (no callback ever crosses back into Python), box constraints enforced by clamping each proposed step into `[lower, upper]` before evaluating it. Not a port of scipy's TRF algorithm — a different, simpler bounded LM — so parity is judged by both fits recovering the same synthetic ground-truth Moffat parameters within tolerance (`tests/test_native.py`), not bit-exact agreement with curve_fit's own iterate path. Numpy/scipy fallback is `_fit_moffat_wing_numpy` (the original `curve_fit` call), unchanged.
- **2D PSF star fit** (`src/psf_deconvolution.py` `estimate_psf`, used by `--deconvolve rl`/`rl-sv`, `--drizzle-kernel psf`, blind-PSF): the same `curve_fit`-callback problem as the Moffat wing fit above, one dimension up — `estimate_psf` fits a 2D Moffat (default) or Gaussian to each of up to `RL_PSF_MAX_STARS` (30) ~31×31 star cutouts, and scipy re-evaluates the Python model (plus numerical differencing) on all ~900 pixels every trust-region iteration. `fit_psf_moffat2d_native` / `fit_psf_gauss2d_native` are a from-scratch bounded LM (shared generic `psf_lm<const N>` + small dense `solve_lin<const N>`) with each model and its analytic Jacobian inlined; same p0/bounds `estimate_psf` built for `curve_fit`. ~4× (measured: a 30-star Moffat PSF estimate 161 ms → 38 ms). Runs once per session, not per frame — a small win on the opt-in deconvolve paths, not a hot-path one. Numpy/scipy fallback is `_fit_star_2d_numpy` (the original per-star `curve_fit`); native/numpy parity + synthetic-ground-truth recovery in `tests/test_native.py`. With this kernel present, `estimate_psf` no longer hard-requires `scipy.optimize.curve_fit`.
- **Background mesh median grid** (`src/background.py` `_process_channel`, inside `extract_background`): unconditional on the default pipeline — background extraction is on by default, and this exact per-cell-median loop shape also runs as a DBE/wavelet-BG fallback whenever patch sampling comes up short (dense star fields), plus the legacy `--bg-method mesh` path — called 9x per stack (1 broad + 2 fine passes x 3 channels). Per-cell `np.median` call overhead dominates at the small cell sizes involved (the fine pass is on the order of ~700 cells/channel), not per-cell compute; `mesh_median_grid` fuses the whole `(ny, nx)` grid into one native pass, parallel over cells. Numpy fallback is `_mesh_median_grid_numpy` (the original nested loop).
- **Local-normalization coarse background grid** (`src/local_normalize.py` `_coarse_background`, `--local-normalize`): called once per frame, so the numpy reference's per-cell `np.percentile` call overhead is multiplied by the session's frame count (e.g. a 200-frame session x 24² grid ≈ 115k tiny percentile calls per run). `local_normalize_grid` fuses one frame's whole grid into a single native pass, parallel over cells. Numpy fallback is `_coarse_background_numpy`.
- **Star-disk mask stamping** (`src/star_removal.py` `build_star_mask`, opt-in via `--remove-stars`): rich star fields hit up to 4000 small per-star Python iterations building the removal mask. `stamp_star_disks` parallelises over output rows rather than stars (a shared mutable mask output rules out per-star parallelism) — each row scans every star's precomputed integer bounding box (a cheap O(1) reject) before applying the exact same disk-membership test the numpy reference uses, `(y - cy)^2 + (x - cx)^2 <= r^2`, so the mask matches bit-for-bit; also returns the max radius actually stamped (over non-empty-bbox stars), matching the Python reference's `max_r_used` bookkeeping exactly rather than recomputing it in Python over all stars including out-of-frame ones.
- **Bresenham line rasterization** (`src/trail_reject.py` `_bresenham_line`, used by `--trail-reject` to fill in a detected satellite/aircraft trail segment): a textbook zero-vectorization case — a sequential line-walk with pure scalar integer arithmetic and no numpy call to hide behind, so it's stuck slow in Python regardless of array size. `bresenham_line_native` is a direct port of the existing (skimage-`draw.line`-validated) symmetric error-term formulation, integer-for-integer, not a redesign.
- **Radial-bin median profile** (`src/denoising.py` `radial_renormalize`, `--comet-mode` only): the numpy reference rebuilds a boolean mask over the *whole* image once per bin (`n_bins` full-image passes, default 200) just to select each bin's pixels before taking the median — wasteful, since bin membership only needs one `O(H*W)` bucket-assignment pass. `radial_bin_median` does exactly that: one pass buckets every pixel's channel value by its radial bin (matching the numpy reference's half-open `[edge[b], edge[b+1])` binning), then a native quickselect median per bucket, parallel over bins. Niche relative to the other kernels above (opt-in comet workflow only), but a real per-call win when hit.

- **Batch aperture photometry** (`src/photometry_core.py` `aperture_photometry_batch`, `--photometry` / `--photometry-timeseries` / `--color-calibrate`): partial-pixel circular-aperture photometry for N star centres at once against an `(H,W,C)` image — per star, per channel: supersampled (`subpix²`, edge pixels only) aperture coverage fraction, robust `(r_in,r_out]` sky annulus (quickselect median + MAD), background-subtracted flux, aperture max (saturation flag), effective area. Rayon-parallel over stars (each writes its own output rows). The numpy mirror (`_aperture_photometry_batch_numpy`) is a per-star Python loop with `mgrid` masks + a vectorised supersample — fine for one stacked frame, but the time-series path calls this N_stars×N_frames times (e.g. 300×200), where that loop dominates: measured **~150× faster** native (300 stars on a 1500×2000×3 frame: 116 ms → 0.8 ms), turning a ~23 s numpy per-run cost into ~0.2 s. Parity-tested in `tests/test_native.py` (rtol 1e-5 vs the mirror across aperture sizes; edge/blank-frame → NaN row; bad-radii → `ValueError`).

- **CFA drizzle splat** (`src/cfa_drizzle.py` `cfa_drizzle_frame`, `--cfa-drizzle`): one pass over a frame's sensor pixels (channel from Bayer parity), affine map to the output grid, bilinear reference lookup + signal-aware rejection, exact area-overlap drop deposit into `num`/`den`/`cov` `(out_h, out_w, 3)` f64. Parallel over 16-row bands of the *output*: each thread owns its rows exclusively (a drop straddling a band edge is deposited by each band into its own rows only; a sample is *counted* once, by the band owning its centre row), so no atomics and no per-thread copies of three full-size f64 planes. Per-row input span solved analytically from the affine, so the scan stays O(samples in band) under rotation. The per-frame noise sigma is computed in numpy on every 7th lattice site and passed in, so both paths use the identical sigma. Numpy mirror `_frame_splat_numpy`; parity in `tests/test_native.py`. **15.7x** (407 s -> 26 s, 148 frames of 2048x3056).

- **Fused drizzle accumulate** (`drizzle_accumulate_lanczos3`, `src/stacking.py` `run_stacking_phase`): the drizzle loop warped each frame into a fresh f32 array, multiplied by the weight and added it into the shared f64 accumulator under a lock -- three full-size passes and a serialisation point (the add alone ~150 ms of ~435 ms per rotated 2x frame, one thread at a time; 16 threads also each held an output-sized buffer, which is what the RAM cap on drizzle threads was for). The kernel produces each output row with `lanczos3_row_flat` (the code `warp_affine_lanczos3` itself runs, extracted so the two cannot diverge), multiplies by `f32(w)` and adds straight into the accumulator, parallel over rows; frames go one at a time with the next frame's load overlapped. **Bit-identical** to warp-then-add (kernel test at 3 rotations x pixfrac, and an end-to-end test through `stack_target`). `--drizzle-pixfrac < 1` used seven full-size f64 temporaries per frame in numpy; the tent weight is now computed per pixel in the same f64 operations (`round_ties_even` = `np.round`). Real-size benchmark, 16 frames of 2048x3056 -> 2x: **385 -> 269 ms/frame (1.4x); with pixfrac 0.7 1193 -> 305 ms (3.9x)**. Only the plain Lanczos-3 path: PSF/magic kernels and `--elastic-registration` keep the thread-pool path. **A test shim that wrapped `_native` and delegated to `st._native` recursed into itself, the resulting `except Exception` silently fell back to scipy, and the 'unfused' reference was a different resampler (2% pixel differences) -- capture the real module before swapping it.**
- **Area-overlap drizzle** (`drizzle_splat_frame`, `--drizzle-method splat`, opt-in): the actual drizzle algorithm rather than a Lanczos gather at every output pixel. Each input pixel is a square drop of side `pixfrac*scale` output px deposited by exact overlap into `num`/`den` (same drop geometry and row-band ownership as `cfa_drizzle_frame`, all three channels sharing a drop). One pass over the *input* -- ~16x fewer multiply-adds than the gather: **59 ms/frame (6.5x vs 385), 55 ms with pixfrac 0.7 (22x vs the old 1193)**. Not equivalent to resample: on a synthetic dithered undersampled scene (48 frames, RMSE against truth) Lanczos resample 35, splat pixfrac 1.0/0.8/0.6 = 44/42/40 -- softer, no ringing, and the drop is axis-aligned in output space (a small approximation under field rotation, as in `cfa_drizzle.py`). Uncovered output pixels stay 0. Falls back to resample, with a printed reason, for `--drizzle-kernel psf/magic`, `--elastic-registration`, no native kernel. Tested against a direct per-pixel area-overlap reference and for flat-field/flux conservation.
- **Fused calibration and hot-pixel kernels** (`calibrate_frame_inplace`, `hot_pixel_bayer`, `hot_pixel_rgb`; `src/debayer.py` `calibrate_frame`, `_fix_hot_bayer`, `_fix_hot_rgb_impl`; crate 0.27.0): Phase 1's calibrate and hot-pixel steps were 34% of its worker time (873 + 1271 ms/frame under 16 workers) and are memory-bandwidth bound: calibration made ~6 full-frame passes and two temporaries (`dark*scale`, the clip's copy); the Bayer hot-pixel fix did, per 2x2 sub-plane, a contiguous copy, a median, a subtraction, an abs and a full-plane `np.median`; the RGB fix built luma from three temporaries, filtered, took a full-frame MAD and recomputed luma. Each is now one native call doing the same f32 operations in the same order, so **bit-identical** (calibration and the Bayer fix to the numpy path; the RGB fix to the box-mean kernel path that shipped before -- the pure-numpy fallback's scipy `uniform_filter` differs from that by an ulp, as it always did). Single-thread real-size frame (2048x3056): calibrate 40 -> 9 ms, Bayer statistical fix 715 -> 29 ms, Bayer hot-map replacement 666 -> 12 ms (computed only at flagged pixels), RGB fix 1174 -> 52 ms. Details that matter for identity: numpy 2 (NEP 50) does `f32_array * python_float` in f32, so `dark_scale` and `1.4826` are rounded to f32 first (the RGB path's `mad` is a Python float, so its sigma is f64 and only the final cut is rounded to f32); `np.median` of an even count is `(a+b)/2` in f32; a NaN anywhere in the |diff| plane makes the MAD NaN and nothing is flagged. `hot_pixel_rgb` returns None for a degenerate MAD (< 1e-6) so numpy's `np.std` fallback still runs. The Bayer kernel takes a hot map *or* a threshold, never both (the numpy path shares one median between them and the pipeline never combines them). float32 masters only; anything else keeps the numpy steps.
- **Fused pre-gradient removal** (`pre_gradient_apply`, `src/frame_processor.py::_pre_gradient_removal`, `pre_gradient_removal`): the per-frame degree-2 surface subtraction built two full-size f64 meshgrids, ~8 f64 temporaries and three luma arrays (349 ms single-thread, **2.7 s/frame under 16 workers = 34% of Phase 1** once the option is on). Only the ~5k sample points' luma is built for the fit; surface evaluation (f64, numpy's operation order), f32 subtraction with the floor at 0 and the new luma are one pass. Bit-identical, 349 -> 8 ms. **`pre_gradient_removal` is one of the choices `--auto` bakes into a saved config**: a first `--auto` run turns it on *after* Phase 1 (so it costs nothing that run), then the saved `_config.toml` sets it before Phase 1 -- re-running from that config makes Phase 1 slower and changes its metrics. That, not a regression, is why a saved-config run looked 'slower' (2665 ms/frame appeared in the breakdown against 0.0 in the run that produced the config).
- **Debayer-adjacent Phase 1 kernels** (`strided_sigma_clipped_median`, `green_equalize_inplace`, `bayer_grid_equalize_inplace`, `hot_pixel_rgb_inplace`, `white_balance_grayworld_inplace`, `luminance_native`; crate 0.28.0): Debayer was the largest Phase 1 step (2.2 s/frame under 16 workers) but the Malvar kernel is only ~72 of its ~336 ms alone -- the rest was numpy around it: `green_equalize` copied the whole mosaic and ran two sigma-clipped medians on strided copies; `_equalize_bayer_grid` ran four more on strided views of the 75 MB RGB array, then `rgb.copy()` and four clip-assigns. Now the medians gather their own strided planes natively (f32 storage, f64 arithmetic -- the same values as the older f64 kernel), the G1/G2 gain and the grid offsets are applied **in place**, and the hot-pixel fix, gray-world white balance and luminance recompute also work in place / in one pass (`inplace=` on `green_equalize`, `_equalize_bayer_grid`, `remove_hot_pixels_rgb_with_lum`, `white_balance_grayworld`; `frame_processor` passes it only when the RGB array came from its own debayer, never when the loaded array *is* the RGB frame). Real Fireworks session, 148 frames, 16 workers, ms/frame: **debayer 2207 -> 1002, hot-pixel 489 -> 310, white balance 255 -> 187, luminance recompute 259 -> 68**. Bit-identical to the previous native path on real frames (rgb, lum and metrics), *not* to the pure-numpy fallback: numpy's `std`/`sum` on float32 accumulate in f32 while the native medians accumulate in f64, a ~3e-8 relative difference that was already there. **Floor:** each sigma-clipped median is ~6 ms per iteration x 3 (the two sequential f64 sums cannot be reordered without changing bits), so six medians are ~150 ms of single-thread work per frame -- a radix-histogram selection was tried and was no faster than quickselect. Getting below that needs a subsampled median, i.e. a change in the result (not done). A band-fused debayer + hot-pixel + white-balance pass is not possible without changing numerics either: each stage needs a whole-frame statistic (G medians, luma-MAD, channel means, the frame max) from the previous stage's complete output. The machine has 8 physical cores under 16 workers, and `_RAYON_WORKER_CAP = 1`, so total work, not span, is what counts.
- **White balance** (`src/debayer.py` `white_balance_grayworld` / `white_balance_whitepatch`, default Phase 1 step): `white_balance_grayworld` (whole path) and `white_balance_apply` (caller-supplied gains, white-patch). The numpy path built ~8 full-size temporaries (`_desaturate_near_clipped_highlights`: per-pixel peak, ceiling, saturation ramp, blend, clip) -- 538 ms per 2048x3056 frame single-thread against ~35 ms of actual arithmetic, and 1.48 s/frame under 16 workers (memory bandwidth). The kernel is one parallel max pass + one fused per-pixel pass, **bit-identical** to numpy (same f32 ops in the same order, no FMA; tested `assert_array_equal` on a real frame, saturated cores, NaN propagation). **Gray-world means are accumulated in float64** (`img.mean(axis=(0, 1), dtype=float64)` rounded to f32; the kernel does the same sequentially). numpy's default float32 `mean(axis=(0, 1))` is a plain sequential float32 sum that drifted ~1.5% on a real frame's red channel, so the previous gains were slightly off; the kernel is still bit-identical to the numpy fallback (crate 0.25.1). Single-thread 543 -> 78 ms (6.9x). cupy arrays and non-float32 gains keep the array path.
- **Fused gray-world white balance + luminance** (`white_balance_grayworld_lum_inplace`, `debayer.white_balance_grayworld_lum`; crate 0.40.0): the in-place gray-world step read the 75 MB RGB frame three times (sequential f64 channel means, a parallel max for the highlight ceiling, the gain pass) and Phase 1 then read it a fourth time to recompute the luminance. The max is order-independent, so it now rides along in the sequential means pass, and the gain pass writes each pixel's luminance from the f32 values it just stored: two reads instead of four, **bit-identical** to grayworld-then-`luminance_native` (incl. Real Sunflower run, 16 workers: white balance + luminance 206 -> 168 ms/frame. (A synthetic 16-process A/B first quoted 209 -> 147 and 6.6 -> 7.1 frames/s; both sides of it had run the new wheel -- `pip install $TEMP/...*.whl` does not expand in Git Bash, where `$TEMP` is a backslash path -- so that figure was noise. - **Run-time AVX2 dispatch for the 3x3 median** (`median3_interior`, `median3_interior_avx2`, crate 0.30.0): the crate builds for baseline x86-64 (SSE2), and a global `-C target-cpu=native` would make the wheel/exe crash with an illegal-instruction error on any CPU without the build machine's instructions (and `native` on a CI runner bakes in whatever that runner has), so it is never used for releases. Measured with it: only the 3x3 median (41.8 -> 22.4 ms) and the two hot-pixel kernels (~20%) gained; Malvar, white balance, calibration, the rotated warp, sigma-clip and bilateral were within 5% (bandwidth-bound, or sequential f64 sums that cannot be vectorised without changing the bits). So just the median's branchless min/max network is compiled twice -- a shared `#[inline(always)]` body, plus a `#[target_feature(enable = "avx2")]` twin chosen by `is_x86_feature_detected!` per row -- and one binary is safe everywhere (other architectures compile the baseline body only). Min/max are exact, so the result is identical. Paired timings, single thread, 2048x3056: median 41-46 -> 25 ms, Bayer hot-pixel 84-92 -> 71-73, RGB hot-pixel 94-100 -> 82-83. `strip = true` is set in `[profile.release]` (symbols are unused at run time; `panic = "unwind"` stays for tract's malformed-model guard).
- **Windowed and table-weight rotated warp** (`warp_affine_lanczos3`'s `origin`, `registration.apply_transform(crop=...)`, crate 0.29.0): Phase 3 warped every full frame and then threw away everything outside the common crop -- 35% of the pixels on the Fireworks session (1497x2705 of 2048x3056), 8% on the Orion combine. `apply_transform(..., crop=(top, bottom, left, right))` now asks the native kernel for just that window; the kernel computes output pixel (oy+row, ox+col) with the *same* arithmetic a full-frame warp uses there (integer offset first, then the f64 maths), so the window is **bit-identical** to slicing the full warp (tested for rotation, translation, scaling, identity, several origins; GPU, elastic and non-native requests warp the full frame and slice). Separately, the general (rotated, non-separable) path takes its per-pixel Lanczos weights from a 4-point-Lagrange table over 512 cells instead of the closed form (~4 trig calls + ~24 divisions per pixel, roughly half of the ~640 ms/frame): **638 -> 416 ms (1.53x) single-thread; 99.985% of the float32 output is bit-identical to the closed form, the remainder differs by ~1 ulp** (max abs 4.9e-4 on values up to ~6000). Not bit-identical overall, so `ORIGINSTACK_LANCZOS_EXACT=1` (read once per process) restores the closed form for A/B checks; the separable table path (translation/drizzle scaling) is untouched. A trap worth remembering: the closed form is 0/0 at r == 1 exactly (a tap lands on the sample), which the table's r=1 node hits although the closed form never sees it -- the node is set to a delta by hand, otherwise 0.7% of the output is NaN.
- **Warp into the aligned stack** (`warp_affine_lanczos3_into`, `registration.apply_transform(..., out=)`; crate 0.41.0): Phase 3's alignment loop copied each source frame out of the frame store (`np.array`, 75 MB), warped into a fresh array and copied that into the aligned stack -- two ~70 MB copies and two fresh allocations (zero-filled by the OS on first touch) per frame. The source is now a view of the frame store and the kernel writes each output row (`lanczos3_row_flat`, the code the allocating kernel runs) straight into the frame's slot: bit-identical (kernel test; a whole Sunflower stack). Sunflower alignment 12.1 -> 10.0 s (158 frames, 16 workers). Non-native/GPU/elastic requests compute as before and copy into `out`.
- **Lanczos-3 affine warp weights** (`warp_affine_lanczos3`, `lanczos6_weights`): a rotated warp is not separable, so every output pixel computed two `lanczos6_weights` calls at two `sin()` per tap = ~24 trig calls a pixel, which was essentially the whole cost of alignment (2187 ms per rotated real frame single-thread). Taps sit exactly 1 apart, so `sin(pi x_t) = -(-1)^k sin(pi r)` and `sin(pi x_t/3)` follow from `sin(pi r/3), cos(pi r/3)` by angle addition: 3 trig calls per axis instead of 12, same maths to ~1e-15. Plus an RGB interior fast path that reads each tap row's 18 contiguous floats once and accumulates the three channels together (per-channel summation order unchanged). **2187 -> 625 ms (3.5x), output bit-identical to the previous kernel** on a real rotated frame (also drizzle's resample, which shares the kernel). Tests: an independent direct-formula float64 Lanczos reference at 5 rotations (rtol 2e-6) and RGB-fast-path == single-channel-loop. **The earlier hypothesis that alignment was disk-bound was wrong**: memmap writes ran at 1.2 GB/s and reads at 2.2 GB/s, the files (11 GB + 6.5 GB) fit in RAM with 54 GB free, and the time was the warp's compute -- measure before assuming an I/O fix.

- **Mosaic spike rejection** (`spike_reject_bayer`, `src/debayer.py::remove_spikes_bayer`, `--spike-reject`, opt-in; crate 0.38.0): per Bayer plane, a pixel is replaced by the median of its 8 same-plane neighbours when it is brighter than all 8, exceeds that median by `SPIKE_REJECT_SIGMA` (5) plane sigmas, by `SPIKE_REJECT_CONTRAST` (5) times the neighbours' own lift over the plane median (a sampled star lifts its 2-px neighbours), and lifts fewer than 3 of its 4 adjacent mosaic pixels above `SPIKE_REJECT_SUPPORT_FRAC` (0.15) of its peak. Sigma (MAD of pixel minus neighbour median) and the plane median come from every other row/column of the plane; a min-of-8 prefilter (exact: the median is >= the minimum) skips the median for ~all sky pixels, and the median of 8 is Knuth's 19-comparator network. **Bit-identical** to `_spike_reject_bayer_numpy` (real frame + 300 random frames with ties/NaN, `tests/test_spike_reject.py`). 1 thread: 169 ms per 2048x3056 frame (first version with a per-pixel sort: ~1060 ms/frame under 16 workers). The brighter-than-all-8 rule is load-bearing: without it the steep wing pixels of undersampled (FWHM 2-3 px) bright stars were flagged. Catches the adjacent 2-pixel hits `hot_pixel_bayer`'s star-support rule keeps. ~200 events per real 20 s Origin sub. **Does not change a >= 20-frame rejection stack** (see the lacosmic correction in the Siril row above); `--auto` turns it on where it wants per-frame CR removal (< 20 frames, mean, drizzle), in place of lacosmic.

**A native port that was tried and reverted** (kept here so it isn't re-attempted blind): fusing `compute_quality_metrics`/`validate_image_data`'s several separate numpy passes (percentile x2 different sets, std, median, MAD, isfinite, count_nonzero) into one native pass — sort once, read off every stat. Measured slower, not faster, on both functions (`validate_image_data` 30ms→75ms, `compute_quality_metrics` 26ms→33ms on a 1936x1096 frame). Root cause: numpy's own multi-percentile call is already a well-optimized C-level operation cheaper than a full `O(n log n)` sort at this scale (measured: `np.percentile(arr, 5 values)` 27ms vs `np.sort(arr)` 15ms — so a full sort was competitive with numpy's own approach at best), and the "fused" version added Python-side `ravel()`+`ascontiguousarray()` copies, an f32→f64 upconversion (2x the memory/cache footprint for the sort), and PyO3 marshalling on top of that sort — the overhead stack outweighed what fusing multiple calls into one saved. Lesson for future kernel candidates: measure the *actual* numpy baseline's algorithm (quickselect-based partial partitioning is not "several dumb passes", it can already be close to optimal) before assuming a native rewrite wins — this project's rewrites win when numpy/scipy is doing something genuinely wasteful (a Python-level loop, a full-image computation for a sparse result, redundant re-detection), not just because "native beats numpy" as a blanket rule.

**Also tried and reverted (2026-10): a sort-based MAD sigma-clip** for `patch_weighted_sigma_combine`. Rejection removes both tails, so the survivors are always a contiguous range of the sorted samples: one sort per pixel-channel, then each iteration's median read off directly and the MAD from a two-pointer merge of the two sides' distances. It was bit-identical to the quickselect path (A/B over ties, NaN, +-0, MAD-0 pixels, 0-5 iterations), but **13% slower** single-thread (335 vs 297 ms on 158 x 100x300x3): sorting 158 values costs more than the ~4 quickselects it replaces. The combine runs at ~3.3 us per pixel-channel (~20 ns per sample per iteration); the bilinear patch-weight sampling is only ~3% of it.

**Sculptor's R/B noise gap vs Siril is sharpness, not noise (2026-10).** 178-frame Sculptor subset, one Siril stack (`bench_vs_siril.py --reuse-siril`): default noise vs Siril 1.23/0.99/1.33 (as on the full 532 frames -- the same ratio at a third of the frames already argued against fixed-pattern noise). Switched off one at a time, nothing closed it: `--white-balance none` 1.17/1.13/1.30, `--no-proper-coadd` 1.24/1.00/1.35, Siril's rejection (winsorized 3/3) 1.23/0.99/1.33, Malvar 1.21/1.03/1.31. White balance *before* the debayer (Siril's `-equalize_cfa` order) gave 0.97/0.94/0.92 but stars 8% wider -- a worse trade than blurring. **Per-channel shared-star widths showed the cause: OriginStack's R/G/B are 4.4/3.6/10% narrower than Siril's** (luma-only width hid it). Each channel blurred to Siril's width (sigma searched, interpolated to width ratio 1.000): noise **1.07 / 0.89 / 1.01**. Compare per channel at matched resolution before calling a channel noisy.

**Two image-domain ideas tested and not kept (2026-10)**, so they are not re-attempted blind (scripts were in the session scratch, not the repo):
- **Demosaic-free luminance** (`L = raw / k`, k = the stack's colour at that pixel, warped back into each frame; two passes, L stacked like a mono channel and paired with the normal stack's colour). Oracle (true k): luminance RMSE 2.4x lower than RCD for FWHM 2-3 px, nothing at 3-4.5 px. Synthetic two-pass, 40 dithered frames: star-core error -28 to -44% at every FWHM, sky noise unchanged. **Real data, same warp and combine for both luminances: Sculptor (531 frames, per-frame FWHM median 2.7 px) stars 4% wider, noise +10%; Sunflower 0.6-1.0% wider, noise +14%**, with k from the whole stack or from the background-subtracted excess (the colour of the star's own light, seeing-independent) alike. At the Origin's sampling RCD loses little and its averaging is what keeps per-pixel noise down; the simulation had perfect registration and no seeing variation. Also consistent with `--cfa-drizzle`'s verdict.
- **Ubercal flat from the stars** (Holmes, Hogg & Rix 2012: `m_sj = M_s + t_j + phi(x, y)`, Legendre phi, robust weighted LSQ). Synthetic recovery of a 0.15 mag vignetting: rms error 0.011 / 0.007 / 0.002 mag at 2 / 10 / 30 deg of rotation. **Real Sunflower, with and without its flat: phi unconstrained even at degree 1 (sigma 2.4-3.3 mag; degree 4: 17-22 mag) against ~0.07 mag of real vignetting** -- only 20-31 stars per session are better than 0.1 mag per frame (per-sub SNR is low), stars move a median 49 px, and a dither translation is exactly degenerate with linear phi + frame zero points. A ridge only returns its prior (with and without the flat: 0.029 vs 0.030 mag range). The only plausible variant is a multi-night fit over sessions with tens of degrees of rotation between them (the five Lagoon sessions span 26.8 deg), not attempted.

The startup banner reports native status (`native_status()` in `src/utils.py`); each accelerated step logs a `[rust] …` line. Separately, Richardson-Lucy deconvolution's FFT iteration (`_rl_deconvolve_xp`) runs on the GPU (cupy FFT) when `--use-gpu` is active and on CPU (numpy/scipy FFT) otherwise — the same xp-generic function either way, validated against skimage's `richardson_lucy` on the numpy backend before skimage was dropped as a dependency entirely (2026-07).

Kernel internals (why they're fast): a blocked **gather-transpose** turns the per-pixel N-sample gather (N huge-stride read streams that defeat the prefetcher/TLB) into sequential per-frame row-segment copies through an L2-resident pixel-major tile; medians use **quickselect** (`select_nth_unstable`, O(n)) instead of a full sort; the warp has a **separable fast path** for pure translation (per-image wx table + per-row wy — zero `sin()` calls per pixel) plus an interior path with no per-tap bounds checks. Measured on top of the first-generation kernels: sigma-clip ~2.6×, winsorized ~3.0×, median ~4.0×, ESD ~1.7×, fused patch combine ~2.8×, shift warp ~6.5×, affine warp ~2.8×, aniso ~4.0× ([tools/bench_native.py](tools/bench_native.py) reproduces the numbers).

Build (needs a Rust toolchain + `pip install maturin`):
```bash
# into a virtualenv:
cd ext/astro_native && maturin develop --release
# system Python (no venv): build a wheel and install it
cd ext/astro_native && python -m maturin build --release
pip install --force-reinstall target/wheels/astro_native-*.whl
```
Optionally set `RUSTFLAGS="-C target-cpu=native"` before building for extra auto-vectorisation — safe when the wheel stays on the machine that built it (do not redistribute such a wheel; it may use instructions older CPUs lack).

Parity vs the numpy reference is covered by [tests/test_native.py](tests/test_native.py) (auto-skips if the module is absent). Benchmark with [tools/bench_native.py](tools/bench_native.py) before/after kernel changes.
