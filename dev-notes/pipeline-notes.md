### Four-phase processing pipeline
1. **Phase 1 — Process & Quality Analysis** — Load, calibrate, debayer, and quality-analyse each frame in parallel (ProcessPool, ThreadPool, or sequential). Chromatic aberration is measured once per session (three sample frames) and applied per frame; L.A.Cosmic is auto-skipped when >=20 frames stack with a rejection method. Patch quality scores for patch-weighted stacking are computed here while the frame is in memory. Hard-limit rejection, statistical outlier detection, and percentile quality threshold filter out bad frames. Handled by `frame_processor.py`.
2. **Phase 2 — Registration** — Coarse-to-fine pyramid seed (half-resolution, integer precision, shared with reference selection) -- below the coarsest level each refinement only needs lags within +-1-2 px of the upsampled seed, so it computes a 5x5 window of the *linear* (zero-padded) cross-correlation directly (`_xcorr_window`, native `xcorr_window`, crate 0.39.0; `_PYRAMID_WINDOW = 2`) instead of a full padded FFT, falling back to the FFT when the peak lands on the window edge. Same values the FFT path argmaxes, so the same shifts: 0 mismatches on 272 real frames (Sunflower, Omega), 156 -> 66 ms/frame, Sunflower pyramid pass 6.9 -> 2.3 s, stack bit-identical plus a 2x-downsampled FFT residual correlation with parabolic sub-pixel refinement (~0.05 px; scipy pocketfft at next-fast-length padding), then optional affine (rotation+scale) via star matching + RANSAC (**seeded**, `registration._RANSAC_SEED`: unseeded, the same session stacked twice could pick different inlier sets and differ at ~1e-4 px in the shifts, rms 1.7 ADU in the stack -- which made bit-identity checks between two runs unreliable). Post-registration residuals are verified on a ~20% sample, escalating to all frames on failure. Frames whose measured residual exceeds the threshold are dropped from the stack by default (`--no-reg-residual-reject` to keep them). The affine branch validates its own fit (shift < 10% of frame size, rotation < 5deg) before accepting it, falling back to translation-only registration otherwise -- a bad RANSAC star match can converge on a wildly wrong but internally-consistent transform, and that failure mode wasn't caught by any downstream check. Optional `--elastic-registration` fits a smooth per-frame local (non-rigid) displacement field from the residual check's matched-star correspondences (reusing DBE's local-regression fitter), correcting spatially-varying distortion a single global affine can't -- composed into the same single resample pass as the affine warp (not a second pass), and honoured by drizzle too. Handled by `run_registration_phase` in `registration.py`. **The residual gate cannot reject a whole session** (`_relative_residual_gate`): when the absolute threshold (adaptive `max(1.5, 3*FWHM/(2*SNR))` px) fails more than half of >= 10 frames while the session's *median* residual is within `REG_RESIDUAL_MAX_PX_CAP`, every frame sharing one modest residual means the threshold is mis-set, so frames are judged against the session's own median + 4 robust sigma (capped). Real case: a saved config switched on `pre_gradient_removal`, which raised the measured SNR 1.7 -> 5.0, shrinking the threshold to its 1.5 px floor against a true median of 1.83 px: 144 of 145 frames rejected, one frame stacked, only a log line to say so. **Saved configs bake in --auto's derived choices** (e.g. `pre_gradient_removal`, `galaxy_mode`, `masked_correlation`) as if the user had set them, which changes Phase 1 and so the metrics later gates depend on -- a config from one run is not equivalent to re-running with `--auto`. **Shift-outlier frames are rescued, not written off**: the pyramid shift is translation-only, so on an alt-az mount the field rotation between the reference and a later frame makes it return garbage (real Fireworks Galaxy session: 0.075 deg/frame, 34 of 148 frames flagged at ~2300-2600 px when the true offsets were a few hundred px; another session flagged 40 of 117). Those frames used to be stacked at zero/coarse shift. `_rescue_outlier` now runs the blind rigid star match on every flagged frame (same sanity limits as the normal affine path) and only falls back to the old handling if that fails.
3. **Phase 3 — Stacking** — Align, crop to the valid common region (eliminates black borders), and combine via the selected method (mean, median, sigma-clip, percentile, ESD, or drizzle). Handled by `run_stacking_phase` in `stacking.py`.
4. **Phase 4 — Post-processing** — Full chain applied to the stacked image (see below). Handled by `postprocess_stack` in `postprocess.py`.

### Post-processing chain (Phase 4)
Applied in order; most steps are on by default:
1. Per-channel hot pixel removal on stacked image
2. Star detection (single pass; mask reused by all steps below)
3. Dynamic Background Extraction (DBE) or legacy mesh extraction
4. Chroma noise reduction — fine pass; optional coarse pass for medium-scale colour blotches (config key `chroma_nr_large_sigma`, object-masked; auto-set for galaxy targets)
5. Sky floor correction (per-channel pedestal removal)
6. (Wavelet denoising -- now the curvelet step 11b below, which runs after the sky pedestal; `--denoiser wavelet` turns its structure protection off)
7. Sky residual correction (broad + fine passes after background extraction)
8. Sky pedestal — scalar lift off zero before the non-negativity clips (prevents black-hole clipping); skippable via `--skip-step sky_pedestal`
9. Bilateral filter denoising — `--denoiser bilateral`
10. ACDNR denoising (adaptive contrast-based) — `--denoiser acdnr`
11. Anisotropic diffusion — `--denoiser aniso` (native/Rust accelerated); edge threshold = `aniso_kappa_sigma` (config, default `Config.ANISO_KAPPA_SIGMA` 1.0) x sky sigma (`postprocess._aniso_kappa`), not a fixed ADU value
11b. Directional (curvelet/shearlet-inspired) wavelet denoising — `--denoiser curvelet`
12. Deconvolution — `--deconvolve rl|rl-sv|tv|sparse` (RL is GPU-accelerated via cupy FFT when `--use-gpu`; `rl-sv` is spatially-variant RL; `sparse` is FISTA in this project's own wavelet basis)
13. Star reduction — `denoising.shrink_stars` narrows each star's profile (FWHM / sqrt(1 + amount), peak and colour kept, noise untouched); on in the galaxy-type presets, `--no-star-reduce`
14. Multiscale local contrast enhancement — on by default, `--no-local-contrast`
15a. Edge-band correction (`background.remove_edge_bands`, skippable via `--skip-step edge_bands`; runs just before 15): per edge and channel, subtracts the significant offset of the sky's row/column-median profile from the adjacent interior over the outer 20% of the frame, tapered to zero at the band's inner boundary. Sky mask excludes stars/emission. On a real stack the sky rose 8-30 ADU toward the edges over 250+ rows (background extraction and the ~177 px-sigma flatten both too coarse near the boundary); this removes roughly half to two thirds of the R excess and leaves G/B edge offsets (a wide bowl, not a strip) alone -- partial, not a fix for the bowl.
15. Final sky flattening + neutralisation — masked large-scale per-channel background removal → neutral grey; skippable via `--skip-step sky_neutralize`

The old local-normalisation step (`--local-normalize`) was **removed**: it did local variance equalisation (÷ local σ), which amplifies background noise; gradient/vignette residual is handled by pre-gradient removal (config key `pre_gradient_removal`, auto-set) + DBE + sky-floor + sky-residual.

The preview JPEG black point is set per target by the auto-advisor (`preview_black_sigma`, overridable with `--preview-black-sigma`); higher values (2–3) clip the sky-noise tail to black for a small target on empty sky.

### Checkpoints and `--from-stack`
`save_checkpoint`/`can_resume` ([src/checkpoint.py](src/checkpoint.py)) carry `stack_fingerprint(args, lights)`: a hash of every light's path/size/mtime plus the repr of each setting read by Phase 1 (`p1`: the CLI group 'Frames & calibration (Phase 1)' + `_P1_EXTRA` config-only names) and by Phases 2-3 (`p23`: the 'Registration & stacking' and 'Comet mode' groups + `_P23_EXTRA`, minus `_P23_IGNORE`, the Phase-4-only members). Taken in `stack_target` before `--auto` or Phase 1 mutate `args`, so identical command lines give identical prints. Changed files or a `p1` setting -> fresh start; a `p23`-only change -> resume from Phase 1 (its accepted-frame list is still valid); a verified checkpoint never expires (the 72 h limit now applies only to legacy checkpoints without a fingerprint, which resume as before). **A new Phase 1-3 attribute that is not in those CLI groups must be added to `_P1_EXTRA`/`_P23_EXTRA`**, or changing it will silently reuse a stale checkpoint. `--from-stack STACK.fits` (`pipeline.postprocess_from_stack`, `-d` then optional) runs Phase 4 alone on a previous run's linear main FITS (`load_merge_stack`, so `RAWSTACK` is required) with its sibling `<stem>_config.toml` auto-loaded as `--config` (explicit flags still win), writing the preview/exports for `-o` (default `<stem>_reprocessed`), never the input. The auto-advisor is not re-run (it classifies from per-frame metrics). Measured: Sunflower 28 s vs 108 s for the full run. The desktop app's `RunManager` routes it too. **Early-step cache**: `postprocess._postprocess_early` is everything up to the sky pedestal (hot pixels, star detection, background extraction, chroma NR, sky floor/residual); it returns `(stacked, pp_star_mask, _pp_sources, _bg_excl_mask)`, the only state the rest of `postprocess_stack` reads (checked by AST when extracted -- a new local crossing that boundary must join the return value). `--from-stack` sets `args._pp_early_cache` (`<stem>_phase4cache.pkl`); the key hashes the stack file's path/size/mtime, `skip_step`, the version, and every `args` attribute `_postprocess_early` reads -- collected from its own source by `_early_args_read`, so it cannot drift. Off with `--aberration-report`/diagnostics (they write files from inside those steps). A hit is bit-identical to recomputing.

### Incremental stacking (`--merge`)
The main output FITS is the linear pre-post-processing stack (`RAWSTACK=True`) with `NFRAMES`/`INTGTIME`/`TOTEXP` headers. `--merge PREV.fits [...]` processes only the new session through Phases 1-3, registers each previous stack onto the new grid (blind rigid star-pattern match in [src/blind_match.py](src/blind_match.py) first — nights differ by arbitrary field rotation on alt-az mounts, and this makes no assumption about the angle — translation-seeded star-match affine and translation-only fallbacks, hard error on failure or <25% overlap), and combines them before Phase 4 runs once on the result: each previous stack is first mapped onto the current stack's flux scale (`merge._match_flux_scale`: per-channel gain + sky offset, Tukey-IRLS on smoothed pixels bright in both -- a 25 s ISO 500 stack is not comparable to a 10 s ISO 200 one in raw ADU, and averaging them as-is mixed two brightness scales), then a per-pixel **inverse-noise-variance** weighted mean inside each warped footprint (`merge._pixel_noise`, MAD of lag-4 pixel differences; falls back to `NFRAMES` weights if any stack's noise is unmeasurable). `NFRAMES` is only a proxy for noise when every session has the same per-frame exposure. Header aggregates are summed, so the output chains into future merges. There is no cross-session outlier rejection (each session already rejected internally); not supported with `--drizzle-scale > 1`. A previous stack's own shape rarely matches the current run's (different dither pattern, different Phase 3 common-crop), so it's zero-padded/cropped onto the current grid first (`src.utils.embed_to_shape`, top-left, pixel coordinates preserved) before registration -- the blind matcher needs no positional correspondence between the two canvases, only relative star geometry, so this is purely a shape-reconciliation step, not an alignment hint. `--transient-detect`'s `_align_reference` ([src/difference_imaging.py](src/difference_imaging.py)) shares this same helper for the identical reason: two independently-stacked sessions of the same target routinely differ in pixel dimensions too. It used to hard-refuse a shape mismatch there; the fix also had to carry a real *valid-data* mask through the warp (not an all-ones one) so the zero-padded border reads as uncovered, not real reference data -- otherwise stars in that padding would report as false 'brightening' transients, the same failure mode the rotation-wedge footprint mask already guards against.

### Streaming memory model
Frames are processed one at a time: load → process → accumulate → free. Memory usage stays at ~1-2 frames regardless of total frame count. This is the core design constraint — never accumulate all frames in memory *unless the machine has room*: the per-session frame arrays (Phase 1's RGB/luminance, Phase 3's aligned stack -- ~12 + 4 + 10.6 GB on a 158-frame Origin session) go through [src/frame_store.py](src/frame_store.py) (`--frame-store auto|ram|disk`). An array goes to RAM only if, when created, it fits in *available* memory minus 20% of total RAM (was 30%: on a 532-frame session that kept the 14.7 GB aligned stack on disk while Windows counted only ~38 of 64 GB available, and RAM placement cut alignment 32.5 -> 16.2 s and stacking 85.8 -> 63.0 s) minus the caller's worker reserve; otherwise it is the temp-file memmap it always was. Under `auto` the aligned stack prefers RAM and Phase 1's arrays prefer disk unless the temp disk would be left with < max(10%, 5 GB) free. Phase 1's arrays, when in RAM, are `multiprocessing.shared_memory` (pool workers attach by a `"shm:<name>"` spec through `frame_store.open_frame_array`; `track=False` so a worker's resource tracker never unlinks them); main-process arrays are plain numpy. Both are `_RamArray` (no-op `flush`). **Measured, with this machine's run-to-run noise at +-20 s (a background GUI stack and VS Code):** aligned stack in RAM made Phase 3 faster in most runs (18.7-27 s vs 25-38 s on disk); Phase 1's arrays in shared memory gave Phase 1 times of 37-52 s, but disk-backed Phase 1 also hit 50 s once, so that spread is not clearly shared memory -- they stay on disk by default anyway, so `auto` saves ~10.6 GB of temp disk per run without touching Phase 1. Output is bit-identical across placements (`tests/test_frame_store.py`, through a real process-pool `stack_target`).

### Key classes and singletons
- **`GpuContext`** — CPU/GPU abstraction; exposes `xp` (numpy or cupy), `xndimage`, `xsignal`. Accessed via module-level `get_gpu()` in `src/gpu_context.py`. GPU path is opt-in via `--use-gpu`. **On a real 4GB card, `--use-gpu` currently measures *slower* than CPU-only for real-shaped sessions** (measured head-to-head on the same real 15-frame session, same machine: 54.4s vs ~37s CPU-only) -- not a hypothesis, a real run. Root cause: Phase 1's GPU-mode worker count is capped by VRAM (`max_gpu_workers`, `Config.GPU_PHASE1_WORKER_MB`=450MB/worker -> ~7 workers on a 4GB card after `GPU_VRAM_RESERVE_MB`), well under CPU-mode's `os.cpu_count()` (16 here), while most of Phase 1's actual work (lacosmic, debayer interpolation, CFA equalization, star detection) stays CPU-native regardless of `--use-gpu` -- only calibration/hot-pixel/white-balance dispatch to GPU at all, so the lost worker-count parallelism isn't compensated by GPU throughput on the steps that do run there. A secondary, smaller factor: `execute_frame_processing`'s GPU-mode quality-metrics thread pool (`_qpool`, CPU-bound star detection/FWHM run concurrently with the GPU workers so they're never idle) used to run at a full uncapped `os.cpu_count()` threads *on top of* the GPU workers, and neither pool is rayon/BLAS-thread-pinned the way CPU mode's `ProcessPoolExecutor` workers are (that pinning is subprocess-initializer-only, and this is all one process under GPU mode) -- real oversubscription, but capping the quality pool to `os.cpu_count() - n_workers` only recovered ~0.7s of the ~17s gap, so it's real but not the dominant cause. **Widening GPU coverage further (e.g. to warp/drizzle) was considered and set aside**: it would add more per-worker VRAM demand, shrinking the already-constraining worker count further, compounding this problem rather than fixing it. The actual fix would be architectural (decouple Phase 1 worker count from VRAM when the GPU-dispatched fraction of work is small, or reduce `GPU_PHASE1_WORKER_MB`'s footprint) and wasn't attempted -- real risk of OOM on other users' cards if the budget is cut wrong, and no evidence yet on whether it would pay off on a larger card. `--use-gpu` stays opt-in. **Routing fix (2026-09): `frame_processor.phase1_uses_gpu`** (`--gpu-phase1 auto|on|off`, default auto) sends Phase 1 to the normal CPU `ProcessPoolExecutor` unless `max_gpu_workers` >= `os.cpu_count()` (VRAM is not the constraint) or the run is sequential (`-j 1`); spawned pool workers get a fresh, inactive `GpuContext`, so they never touch the card, and later phases still use it. Decided once per Phase 1 and remembered on `args._phase1_gpu` so the session-CFA probe (now `allow_gpu=False` -- on the GPU path it returned a cupy array and silently disabled session CFA) and a checkpoint reload agree. Session CFA equalisation therefore now runs under `--use-gpu` too. Not re-measured on the 4 GB card (no CUDA on the dev machine at the time) -- the decision logic is unit-tested (`tests/test_phase1_gpu_routing.py`), the CPU path it selects is the one measured at ~37 s.
- **`Config`** — Central class for magic number constants (thresholds, defaults) in `src/models.py`.
- **`FrameInfo`** — Dataclass holding path, type, header, quality metrics, and computed shift for each frame.
- Master calibration frames (bias/dark/flat) are plain numpy arrays stored in a `masters` dict passed through the pipeline.

### Hierarchical vs. single-folder mode
Auto-detected at runtime:
- FITS files in root → single-folder mode (one output FITS).
- Subfolders containing FITS → either **combined-sessions** mode (pool every subfolder's lights into one stack) or **hierarchical** mode (stack each subfolder independently, then combine). `--mosaic` always needs per-subfolder panels; an explicit `--combine-sessions`/`--hierarchical` wins next; otherwise `_want_combine_sessions` in [src/cli.py](src/cli.py) **picks from the data**.

`_predict_rotation_spread` reads metadata only — each session's `info.json` (target + GPS) and the first/last *light* header for the times — and returns the parallactic-angle spread, so the decision is free and happens before any stacking. Above `_ROTATION_SPLIT_THRESHOLD_DEG` (3°) the sessions are stacked separately. Pooling used to be unconditional on the reasoning that a multi-night directory is the common case; that is exactly the case where it costs most, because on an alt-az mount the field rotates as the target tracks, and Phase 3's common crop keeps only what *every* frame covers — 26.8° and 42% of the frame across five real Lagoon sessions. Two things this got wrong on the first attempt, both worth keeping in mind: the metric must be **avoidable** rotation (total spread − the largest any single session covers), since 15 minutes of tracking already sweeps ~3.6° and a lone session would be told to split away from itself; and the light frames must come from `discover_frames`, not a `*.fits` glob, because a flat's `DATE-OBS` is `'0-00-00T00:00:00'` and sweeping one in makes the span unparseable, silently disabling the whole prediction. Unreadable metadata returns `None` and keeps the previous pooling behaviour rather than guessing. `_want_combine_sessions` honours a `combine_sessions=True` **value**, not just membership in `_explicit_cli_dests` (built from argv alone, so a saved `--config` was silently overridden); only `True` counts, since a saved config also records the default `False`. A FITS `TIMEZONE` is validated as `+/-HHMM` before being appended to `DATE-OBS` (`_TZ_OFFSET_RE`), a failed prediction says so on the console, and the reason goes to the debug log. Light headers come from `discover_frames`' own `FrameInfo.header`, not a second `getheader` per file. **Guarded by a test that breaks astropy's `sidereal_time`**: the packaged exe has no IERS tables, and this runs on the default path.

The hierarchical combine itself goes through `merge.merge_previous_stacks` — the same blind, rotation-agnostic star match `--merge` uses ([src/blind_match.py](src/blind_match.py)), with a per-pixel `NFRAMES`-weighted mean inside each warped footprint (a deep session isn't diluted by a shallow one) and the *deepest* stack as the reference grid. It previously used `calculate_shift`, which returns a pure `(dy, dx)` translation and cannot represent rotation at all, so on exactly the alt-az data above it smeared stars toward the corners — and silently, since a shift search returns a plausible number either way. A failure now raises with the per-target stacks kept on disk rather than falling back to that composite. **Phase 4 runs once, on the combined stack, not on each session**: when several sessions are stacked separately, `process_directory` sets `args._defer_phase4` for those `stack_target` calls (reset straight after, so it is never part of a target's snapshotted settings), and `stack_target` skips `postprocess_stack` (and `--uncertainty-propagate`, which is a Phase 4 re-run) -- the combine reads each session's *linear* FITS, so nothing Phase 4 does to a session can reach the result, and it is the slowest phase (N+1 chains became one). A single session, a filter-split group and the combined stack itself are not deferred. **The combined stack goes through Phase 4** (`cli._postprocess_combined`), like `--merge`: it used to be only a linear stack with a linear preview, so the deliverable of a multi-session run never got background extraction, denoising or a stretch. It uses the reference target's own effective args (`_effective_args`, captured per target before `_restore_args`, because `--auto`'s settings live only on the shared args object); the frame list is empty, so measured-FWHM lookups take their defaults. The FITS stays linear (`RAWSTACK`). The **reference grid is the stack with the most integration time** (`INTGTIME`, falling back to `NFRAMES` only if any stack lacks it): 100 frames of 10 s and of 30 s are very different amounts of light. `merge_previous_stacks` trims 3 px off each warped footprint (`_FOOTPRINT_TRIM_PX`; a warped stack's rim blends with the zero fill and Lanczos rings against it, which drew tilted-rectangle outlines across a real five-session combine -- guard `iterations > 0`: scipy's `binary_erosion(iterations=0)` erodes until nothing is left). The combined output's header is seeded from the *reference* stack (`merge.seed_reference_header`: its `INTGTIME`/`TOTEXP`/dates, `RAWSTACK=True`) before `apply_merge_header` adds the others -- that function is written for `--merge`, where the header already holds this session's totals and every aggregate is guarded by "already present", so on the fresh hierarchical header every guard skipped and the output lost its totals and was not marked linear (so could not chain into `--merge`/`--transient-detect`). The reference grid is chosen from `merge.read_merge_meta` (header only), not by loading every stack's pixels to read one integer.

**One shared `args` across targets**: `--auto` mutates `args` in place, and `process_directory` loops every target against the same object, so it snapshots the user's baseline and restores it before each target. Settings the advisor *recomputes* self-correct; **accumulating** ones don't — `skip_step` is appended to under a "not already present" guard, so a nebula target's `sky_residual` skip used to leak into every later target, silently (the target that would have logged the append never ran it). Mutable containers are copied on restore, not aliased, or the first target pollutes the baseline itself and every later restore replays the leak ([tests/test_auto_state_isolation.py](tests/test_auto_state_isolation.py) asserts both halves). The reset is `cli._snapshot_args` / `_restore_args` (module-level so it is testable, with the copy rule in `_copy_arg_value`), and `_restore_args` also **deletes attributes a target created** -- `_ptc_gain_e_per_adu` and friends are set conditionally and read later, so restoring only the baseline keys leaked a calibrated target's measured gain into a calibration-less one. `tests/test_auto_state_isolation.py` drives the real helpers and `process_directory`; an earlier version tested local copies of them, so removing the copy rule from `cli.py` left every test green.

### Optional dependencies (graceful degradation)
Each `src/` module wraps its optional imports in `try/except`. Features degrade gracefully when packages are absent:
- `tqdm` — progress bars (falls back to plain iterator)
- `Pillow` — preview JPEG generation
- `psutil` — memory-adaptive worker/memmap sizing (every use is `try/except`-guarded with a fixed fallback; `src/utils.py` `HAS_PSUTIL`)
- `cupy` — GPU acceleration (`--use-gpu`)
- `rawpy` — camera RAW input (CR2/CR3/NEF/ARW/DNG/…, `src/io_raw.py`); RAW files are silently excluded from discovery when absent
- `tifffile` — TIFF input (`src/io_tiff.py`) and `--export tiff` output
- `astro_native` — optional Rust hot-path kernels (see below); numpy fallback when absent

### Input formats
Besides FITS, the pipeline reads camera RAW (`src/io_raw.py`, needs `rawpy`), TIFF
(`src/io_tiff.py`, needs `tifffile`), XISF 1.0 (`src/io_xisf.py`, no dependency — hand-rolled
reader, counterpart to `xisf_writer.py`'s writer; covers uncompressed/attached float32/
uint16/uint32 mono or RGB data, raises a clear error on compressed or embedded-block XISF),
and SER planetary/lucky-imaging video (`src/io_ser.py`, no dependency). All formats route
through `src/io_fits.py::load_frame`, the single dispatcher every loader (including
`make_master`) uses. A `.ser` file holds many frames; `discover_frames` expands it into one
virtual `FrameInfo` per frame (`path::index`, e.g. `Jupiter_2024.ser::1042`) — `::` isn't a
filesystem separator, so it flows through filename-based classification, logging, and
checkpointing unmodified. Mono SER/XISF frames (unambiguous — never a raw Bayer mosaic) are
replicated to 3 channels at load time to skip debayering; a mono TIFF is inherently ambiguous
(could be a real mono capture or an undemosaiced Bayer export) and falls through to the same
session-Bayer/RGGB default a headerless FITS Bayer frame would — supply a `.json` sidecar
with `bayerPattern` to override.


### Plate solving
`--plate-solve`; backend `--plate-solver auto|local|astap|astrometry` (default `auto` = local, then astrometry.net if it fails, a key is set and the run is online). **Built-in solver** ([src/local_solve.py](src/local_solve.py)): Gaia DR3 tiles (5 deg Dec bands, ~5 deg RA cells, brightest 3000 below G=15, ~120 stars/deg^2) in `star_index_dir()` (`$ORIGINSTACK_STAR_INDEX`, else `%LOCALAPPDATA%\OriginStack\star_index` / `~/.cache/originstack/star_index`); missing tiles are fetched through `net_query` (so `--offline` blocks it) and cached; `tools/build_star_index.py` pre-fills. Hint-driven, not all-sky blind: `hint_from_header` takes an existing TAN WCS (searched half a field around, since it can be off -- see below), else `RA`/`DEC`/`OBJCTRA` keywords, and a scale from the CD matrix or `FOCALLEN`+`XPIXSZ`. Per candidate centre (half-field rings out to the search radius) x trial scale (2% steps) x parity, the catalogue is projected to trial pixels and matched with `blind_match.match_rigid_unknown_rotation` (native), refined to a full affine by iterated mutual-NN least squares, re-centred on the image centre; accepted at >= max(8, 25% of the smaller list) inliers and <= 1.5 px rms. Image stars: the matched-filter detector with the `registration_stars` k_confirm ladder (22/12/8/6), then **halo exclusion** -- fainter detections within `25*sqrt(flux/median)` px of a bright one are dropped (a mag-1.7 star put 14 of the top 40 detections within 211 px of itself). Measured: Sunflower stack 0.5 s from cache, 81 stars, 0.26 px rms; Crab full run 128 stars, 0.24 px; independently, 48/54 in-field Gaia stars land within 2 px of a detection (median 0.12 px). A 3-light, 4-star Epsilon Orionis session does not solve (correctly declines). astrometry.net needs `ASTROMETRY_API_KEY` (direct HTTP via `src/net_query.py`). `apply_network_policy` keeps `plate_solve` under `--offline` for auto/local (`_OFFLINE_OK`).

**Stack WCS (fixed 2026-09).** The info.json solve describes the session's *first* sub (centre within 3" of a Gaia solve of Light0001; later subs drift ~100" away), and `build_wcs_keywords` used to write it mirrored (textbook east-left `CDELT1 = -psx`; real Origin FITS have RA increasing with +x -- measured on Crab and Sunflower, pinned in `tests/test_stack_wcs.py`) at the raw frame centre onto a registered, cropped stack: 0 of 53 Gaia stars within 2 px, median 63 px off. Now `pipeline._settle_stack_wcs` runs right after Phase 3: `session_info.stack_wcs_keywords` maps the first sub's WCS through *its* registration transform and the crop (CD carried by the local Jacobian, so field rotation between that sub and the reference is honoured; falls back to the earliest accepted sub if the first was rejected) -- median 3.9 px, i.e. the accuracy of Origin's own solve -- then, unless `--no-wcs-refine`, refines it with `local_solve.solve_header` (fetches missing Gaia tiles when online; README discloses it): 49/52 within 2 px, median 0.24 px. The result lives on `args._stack_wcs` and is what Phase 4's physical sky model, `--photometry-timeseries` (`_cropped_session_wcs_header(stack_wcs=...)`) and `populate_fits_header` read. A phase-3 checkpoint resume has no transforms, so it maps with shifts only and relies on the refine.

### Object annotation
`--annotate` circles and labels bright stars and named deep-sky objects (galaxies, nebulae, clusters) on a copy of the preview (`<output>_annotated.jpg`; the main FITS/TIFF/JPG are untouched), via the FITS header's WCS and live SIMBAD cone-search queries (`src/net_query.py`, `src/annotation.py`). Needs a WCS solution — `--plate-solve`, or a session `info.json` that already provided one — skipped with a message otherwise. Two separate SIMBAD queries (stars via a `basic`+`flux` V-magnitude join, capped by `--annotate-mag-limit`; DSOs via `basic` restricted to a curated object-type set *and* a Messier/NGC/IC name prefix, to avoid flooding a rich field with SIMBAD's thousands of obscure catalog entries) rather than one combined query, since an inner join on `flux` would silently drop extended objects that lack a clean V-magnitude entry.

### Photometry
Two entry points, both against Gaia DR3, both needing a WCS (Origin `info.json` session solve or `--plate-solve`). Shared machinery: `photometry.match_gaia_field` (detect stars → Gaia cone-search → project via WCS → pixel cross-match), `photometry_core.aperture_photometry_batch` (native partial-pixel aperture + robust sky annulus, numpy mirror), and `observing_geometry.airmass` (site GPS + RA/Dec + UTC → Kasten-Young airmass).

**Catalogue queries are ordered brightest-first** (`net_query.gaia_cone_search(order_by='phot_g_mean_mag')` by default; `vizier_cone_search(order_by=)`, the 2MASS fallback uses `Jmag`): `TOP n` without `ORDER BY` lets the TAP server return *any* n rows of a cone holding more -- a different subset per call. The same Sunflower stack matched 72-78 Gaia stars on four runs of identical code; ordered, **342 on every run** with byte-identical photometry CSVs (the arbitrary subset was mostly stars below the detection limit). `local_solve` and `annotation` already ordered theirs. **`--photometry`** ([src/photometry.py](src/photometry.py)) runs on the linear pre-Phase-4 stack after the WCS is settled (before `--color-calibrate` mutates it). Per-channel aperture photometry (radius from measured FWHM), then a robust per-channel fit `m_cal = m_inst - k·X + ZP + CT·(BP-RP - ref)` against Gaia RP/G/BP (coarse OSC mapping — not a filter-matched transform, ~0.05 mag absolute). `CT` (colour term) is fit only with `--photometry-color-terms`; otherwise it's a plain sigma-clipped median and `CT=0`. Airmass `X` from `info.json` GPS + field centre + obs time (`DATE-OBS`, else `info.json` `dateTime`; Kasten-Young); with no location/time the `k·X` term is dropped and the ZP absorbs mean extinction. Nominal `k` R/G/B = 0.09/0.15/0.23, `--photometry-extinction-k` overrides. Per-source Poisson error uses `--photometry-gain`, else the PTC estimate from raw bias+flat pairs ([src/gain_ptc.py](src/gain_ptc.py), auto-run in `_build_masters`), else header `GAIN`/`EGAIN`. Outputs `<output>_photometry.csv` (per-star `source_id`, x/y, RA/Dec, Gaia G/BP/RP, per-channel flux/mag/magerr/SNR, saturation flag) + `MAGZP_R/G/B`, `MAGZPE_R/G/B`, `MAGCT_R/G/B`, `PHOTCREF`, `PHOTNSTR`, `PHOTAIRM`, `PHOTGAIN`, `PHOTAPR` header keywords.

**`--photometry-timeseries`** ([src/photometry_timeseries.py](src/photometry_timeseries.py)) runs right after Phase 3, while the registered frames are still in `mem_rgb` (so it must run there, not in the post-output section — and it therefore relies on the session `info.json` WCS, since `--plate-solve` runs later). It warps + crops each sub, aperture-photometers the fixed `match_gaia_field` star list on every frame, then iteratively fits an ensemble differential zero point per frame per channel (comparison stars: well-detected in ≥80% of frames, never saturated, mid-brightness; high-scatter members are clipped out over 4 iterations). Writes `<output>_lightcurves.csv` (one row per frame×star: `mjd`, `airmass`, per-channel `mag`/`magerr`, `flag`) and `<output>_lightcurve_stats.csv` (per star: `n_points`, mean/rms/MAD/ptp mag, reduced χ² vs a constant, `is_ensemble`, and a `variable` flag = χ²_red > 3 ∧ rms > 3·median(magerr) ∧ no saturation ∧ not itself a comparison star). `--photometry-target "RA,DEC"` (degrees) or `"px:X,Y"` (stacked-image pixels) marks one star, flags it in both CSVs, and prints its light-curve stats. Differential only — extinction cancels in the ensemble (same field), airmass is recorded but not applied, and there is no absolute zero point.

### Debayering options
`--debayer-method` has three choices (default `rcd` since 2026-10), all native Rust kernels with a numpy fallback, no external dependency (see "Native (Rust) acceleration" above):
- `malvar` — Malvar-He-Cutler (default until 2026-10; fastest, ~0.46 s/frame under 16 workers vs rcd's ~1.9).
- `rcd` (**default**) — Ratio Corrected Demosaicing (Luis Sanz Rodriguez; Siril/RawTherapee/darktable default), `src/debayer.py::debayer_rcd`, native `debayer_rcd_native` (crate 0.38.0). Ported from the published algorithm (no reference implementation vendored), full-frame rather than RawTherapee's tiles; scaled by the frame maximum (ratio terms are scale-free, `eps` assumes [0, 1]), 4-px border from Malvar. Validated against ground truth, not a reference: lower MAE than Malvar on every synthetic scene and ~10% less retained noise; real-data noise numbers in the Siril row of the module table. Native is a port in **f32** (the numpy mirror is f32 too), bit-identical to the mirror. How it got fast, in order (single-thread / 16 concurrent processes per frame): f64 per-tap-mirror original 1.13 s; intermediates stored reflect-padded by 5 px (`rcd_pad_in_place` == `np.pad(mode='reflect')`) 0.71 s; each stage a branch-free loop over contiguous row slices, computed at every pixel then selected per site (as numpy does), so it vectorises 0.32 s; a run-time AVX2 twin (`rcd_core_avx2`; the body is a macro so the stage closures are lexically inside the `#[target_feature]` fn and inherit it -- no FMA, so identical bits) 0.28 s / 1.26 s. **Under load it was DRAM-bound**, not compute-bound: ~14 frame-sized arrays, ~1.3 GB of traffic per frame (Malvar 0.08 s alone -> 0.09 s with 8 processes; RCD 0.28 -> 0.76). Strips alone made it *worse* (each ~1 MB array a fresh OS allocation zero-filled on first touch); with a buffer pool (`RCD_POOL`, every stage array fully overwritten so reuse needs no clearing) and **2-D tiles** (`RCD_TILE` 128 + `RCD_HALO` 12: RCD's reach is ~10 px, tiles start on even rows/cols so parity is unchanged, the frame's own edges keep the reflect padding) it is 0.29 s alone / **0.72 s with 16 processes** (tile 96: 0.78, 192: 0.79). **Later (crate after 0.46.0): tiles are 128 x 256** (`RCD_TILE_X`; halo overhead 1.30x instead of 1.41x; 320-384 wide the same, 512 slower), each tile's planes are written straight into the output (no per-tile interleaved buffer), and the session-constant 2x2 green grid is fused into that write (`debayer_rcd_native_into(..., grid=)`; `_apply_fixed_grid` did four strided read-modify-write passes over the 75 MB output, ~40 ms alone / ~145 ms under 8 processes; the 4-px Malvar border gets it from `_apply_fixed_grid_border`). Bit-identical (52 real/synthetic cases incl. all patterns and NaN; `test_rcd_into_fused_grid_matches_separate_grid`). Debayer bracket on real Sculptor frames into fresh file-backed slots: 133 -> 85 ms alone (2 rayon threads), 540 -> 378 ms with 8 processes x 2 threads. First-touch page faults on the disk-backed frame-store slot are ~40 ms alone / ~175 ms under load of what remains (measured against a pre-touched buffer) -- not addressed. **Pre-touching tried (2026-10), no gain:** 8 processes writing 75 MB frames into fresh slots of a file-backed memmap (each opening its own view per frame, as `_parallel_frame_worker` does) took 60-99 ms/frame; with every page first touched by a thread in the parent, 68-72 ms; the same copy into an already-touched private buffer, 10 ms. The parent's touches do not reach a worker's view -- the worker still faults every 4 KB page of the slot it writes, and each slot page is written exactly once -- so the cost belongs to the writer's own mapping. Shared-memory Phase 1 arrays and file writes instead of slot assignment were already tried (CLAUDE.md). Sunflower end to end 2m03 -> 1m35 (Malvar default was 1m48). `_rcd_raw` is the bare kernel; `debayer_rcd` adds the grid correction. **The wrapper cost as much as half the kernel** (stage timers: 151 ms of RCD stages in a 288 ms single-thread call): it made a float64 copy of the frame to read its max (now `np.fmax.reduce` on the float32 data, same value) and ran a *full-frame* Malvar for the 4-px border (now four 12-px edge strips -- Malvar is a 5x5 local kernel, the strips keep the frame edges and start on even rows/columns, so the border is bit-identical; `tests/test_debayer_rcd.py`). 288 -> 198 ms single-thread, Debayer 1165 -> 823 ms/frame under 16 workers, Sunflower stack identical. **Tried, no gain:** computing each RCD stage only at the Bayer sites whose values are read (exact -- every read lands on the same parity) was 285 -> 369 ms single-thread: the step-2 loops stop vectorising; skipping the diagonal stage's non-target rows (vectorisation kept) was within noise, since that stage is ~7% of the kernel.
- `menon2007` — Menon (2007) DDFAPD directional filtering (`src/debayer.py::debayer_menon2007`, native kernel `ext/astro_native/src/lib.rs`'s `debayer_menon2007`). Ported from and validated bit-exact against the `colour-demosaicing` package's reference implementation (`tests/test_debayer_menon2007.py`, validation-only dependency). Higher fidelity than malvar on fine periodic photographic detail in general, but `tools/bench_debayer_quality.py`'s synthetic-astro-frame benchmark shows only a modest gain (~14% lower MAE on a synthetic starfield) at real cost (~4-5x slower even natively) — most astro frames are smooth sky + point sources, not fine texture, so malvar stays the default. Unlike malvar's single fused per-pixel gather, Menon's per-pixel direction decision depends on a 5x5-diffused gradient of a shifted colour-difference signal — genuinely sequential stages, ported as the same staged full-array passes (each parallelised across rows) the numpy reference uses rather than one fused gather.

`vng` (formerly a cv2-only algorithm, then an alias for malvar once cv2 was dropped) was removed as a redundant choice. `debayer_bilinear` (pure numpy) still exists in `src/debayer.py` as the base debayer function and internal fallback, but isn't reachable via `--debayer-method`.


### Parallelism
- `-j N` (or `--parallel N`) controls worker count. `0` = auto (default), `1` = sequential, `N` = N processes.
- Uses `ProcessPoolExecutor` for CPU multi-process, `ThreadPoolExecutor` for GPU or thread-parallel paths.
- GPU mode auto-limits workers based on available VRAM.

### Packaging the desktop app (Windows)
[packaging/](packaging/) builds the desktop app (`desktop_app.py`) into a standalone `OriginStack.exe` via PyInstaller — no Python/pip install required by the end user:
```powershell
.\packaging\build_windows.ps1
.\packaging\verify_build.ps1   # launches the real exe, confirms the window appears and astro_native (not the numpy fallback) loaded, confirms clean shutdown
```
Output: `packaging\dist\OriginStack\` (onedir — instant startup, unlike onefile which re-extracts the whole numpy/scipy/astropy payload on every launch) plus a zipped `OriginStack-<VERSION>-windows-x64.zip`. `VERSION` (repo root) is read at runtime via `read_version()` (`src/utils.py`) and shown in the window title; bump it alongside each release tag. `ext/astro_native` must be built as a real wheel (`maturin build --release` + `pip install`, not the dev-mode `maturin develop --release` editable install used elsewhere in this doc — PyInstaller's static analysis can't see into an editable/`.pth` install) — `build_windows.ps1` handles this. `.github/workflows/release.yml` attaches the built zip to an already-existing `v*` GitHub Release (never creates one, matching this repo's manual `gh release create` pattern) on tag push. Full details, prerequisites, and known limitations (unsigned exe / SmartScreen, Windows-only) in [packaging/README.md](packaging/README.md).
